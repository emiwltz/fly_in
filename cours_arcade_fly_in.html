Comprendre Arcade dans le contexte de Fly-in

Ce document t'aide a comprendre comment utiliser la librairie arcade pour construire une visualisation du projet fly_in. Il ne donne pas l'algorithme de routing ni la simulation finale: il explique les concepts et la syntaxe dont tu as besoin pour les construire toi-meme.

Python 3.13 dans ce repo arcade 3.3.3 installe visualisation de graphe simulation tour par tour pas de solution cle en main

1. Ce que tu dois apprendre

Dans Fly-in, Arcade n'est pas la partie qui resout le probleme. Arcade sert a afficher ce que ton parser, ton graphe, ton pathfinding et ta simulation produisent. La responsabilite principale d'Arcade est donc la visualisation: zones, connexions, drones, tours, attentes, mouvements en cours et informations utiles pour comprendre la simulation.

Parser

Lit les fichiers maps/*.txt et transforme le texte en objets Python.

Simulation

Decide, tour par tour, quels drones bougent, attendent ou transitent.

Arcade

Affiche l'etat courant sous forme graphique et rend la simulation lisible.

Question a garder en tete: quand tu ecris une ligne Arcade, es-tu en train de modifier les regles du projet ou seulement leur representation visuelle? Dans une bonne architecture, Arcade ne decide pas du chemin optimal. Arcade affiche les decisions prises ailleurs.

3. Le modele mental d'Arcade

Arcade est une librairie evenementielle. Tu ne fais pas une boucle while True toi-meme. Tu donnes a Arcade des methodes speciales, puis arcade.run() lance la boucle principale et Arcade appelle tes methodes au bon moment.

Tu n'appelles pas on_draw

Arcade l'appelle quand il faut redessiner l'ecran.

Tu n'appelles pas on_update

Arcade l'appelle regulierement avec delta_time, le temps ecoule en secondes.

Tu mutates ton etat dans on_update

Positions animees, timer, pause, vitesse, progression visuelle.

Tu dessines dans on_draw

Tu lis l'etat courant et tu le representes, sans changer la logique du projet.

4. Window vs View

C'est probablement la confusion principale dans arcade_test.py. Une Window est la fenetre reelle de ton systeme. Une View est un ecran logique affiche dans cette fenetre: menu, visualisation, pause, aide, resultat final, etc.

Concept Possede quoi? Quand l'utiliser?
arcade.Window La vraie fenetre, la taille, le titre, le contexte OpenGL. Pour un programme tres simple ou pour contenir des vues.
arcade.View Un ecran actif avec ses propres callbacks on_draw, on_update, input. Pour separer plusieurs ecrans ou garder une architecture claire.
window.show_view(view) Active une vue dans une fenetre deja creee. Quand tu veux passer de menu a simulation, ou afficher une aide.

Pattern simple: tout dans une Window

A utiliser pour un mini test. C'est le plus court, mais moins flexible si ton projet grandit. 

import arcade


class FlyInWindow(arcade.Window):
    def __init__(self) -> None:
        super().__init__(900, 600, "Fly-in viewer")
        self.background_color = arcade.color.BLACK

    def on_draw(self) -> None:
        self.clear()
        arcade.draw_text(
            "Fly-in",
            self.width / 2,
            self.height / 2,
            arcade.color.WHITE,
            font_size=32,
            anchor_x="center",
            anchor_y="center",
        )


def main() -> None:
    FlyInWindow()
    arcade.run()


if __name__ == "__main__":
    main()

Pattern conseille pour Fly-in: Window + View

Une seule fenetre, plusieurs vues possibles. La vue recoit les donnees du projet et s'occupe de les afficher. 

import arcade


class SimulationView(arcade.View):
    def __init__(self) -> None:
        super().__init__()
        self.turn = 0

    def on_show_view(self) -> None:
        self.window.background_color = arcade.color.BLACK

    def on_draw(self) -> None:
        self.clear()
        arcade.draw_text(
            f"Tour {self.turn}",
            24,
            self.window.height - 40,
            arcade.color.WHITE,
            font_size=18,
        )

    def on_key_press(self, symbol: int, modifiers: int) -> None:
        if symbol == arcade.key.SPACE:
            self.turn += 1


def main() -> None:
    window = arcade.Window(1000, 700, "Fly-in viewer")
    view = SimulationView()
    window.show_view(view)
    arcade.run()


if __name__ == "__main__":
    main()

A eviter: creer une window = arcade.Window(...), puis creer une classe GameView(arcade.Window), puis faire window.show_view(game). Si tu utilises show_view, la classe a afficher doit heriter de arcade.View, pas de arcade.Window.

5. Cycle de vie d'une classe Arcade

La syntaxe Arcade devient beaucoup plus claire quand tu sais quoi mettre dans chaque methode.

Methode Quand Arcade l'appelle Dans Fly-in, tu y mets quoi?
__init__ Quand tu crees l'objet. Stocker la map, initialiser les attributs, preparer les couleurs, creer des listes vides.
setup Tu l'appelles toi-meme si tu veux reinitialiser. Remettre la simulation au tour 0, recalculer positions ecran, vider les drones visuels.
on_show_view Quand la vue devient active. Definir la couleur de fond, reset camera si besoin.
on_draw A chaque frame dessinee. Effacer l'ecran, dessiner connexions, zones, drones, labels, UI.
on_update(delta_time) Regulierement, avant le dessin. Faire avancer une animation, accumuler un timer, declencher un tour si lecture automatique.
on_key_press Quand une touche est pressee. Space prochain tour, R reset, P pause.
on_mouse_press Quand la souris clique. Selectionner une zone, afficher ses capacites, son type, ses drones.

6. Coordonnees: carte vs pixels

Dans les fichiers de map, les hubs ont des coordonnees entieres comme start 0 0 ou goal 4 0. Arcade dessine en pixels. Tu dois donc convertir les coordonnees de graphe vers les coordonnees ecran.

Coordonnees Arcade

Origine en bas a gauche. x augmente vers la droite. y augmente vers le haut.

Coordonnees Fly-in

Coordonnees logiques de graphe. Elles indiquent la forme de la carte, pas des pixels.

Transformation mentale

Tu veux une fonction qui prend (zone.x, zone.y) et renvoie (screen_x, screen_y). Elle doit tenir compte des limites de la map, d'une marge autour du dessin et d'un facteur d'echelle. 

def world_to_screen(
    x: int,
    y: int,
    min_x: int,
    min_y: int,
    scale: float,
    margin: float,
) -> tuple[float, float]:
    screen_x = margin + (x - min_x) * scale
    screen_y = margin + (y - min_y) * scale
    return screen_x, screen_y

Cette fonction n'est pas du pathfinding. C'est uniquement une traduction visuelle. Tu peux la tester sans simulation: parse une map, dessine les hubs, verifie que leur disposition ressemble au fichier.

Calculer une echelle correcte

L'idee est de regarder les minimums et maximums de toutes les zones, puis de choisir une echelle qui rentre dans la fenetre. 

# Pseudo-code volontairement incomplet.

scale_x = available_width / max(1, max_x - min_x)
scale_y = available_height / max(1, max_y - min_y)
scale = min(scale_x, scale_y)

7. Dessiner un graphe avec Arcade

Pour Fly-in, tu peux commencer avec les primitives de dessin. Pas besoin de sprites au debut. Un graphe est naturellement compose de lignes, cercles et textes.

Element Fly-in Primitive Arcade simple Pourquoi?
Connexion arcade.draw_line(...) Une arrete entre deux hubs.
Zone normale arcade.draw_circle_filled(...) Un noeud rond est lisible.
Zone bloquee Cercle gris + croix ou contour rouge Doit etre visuellement identifiable comme interdite.
Capacite arcade.draw_text(...) ou arcade.Text Afficher max_drones aide a comprendre les blocages.
Drone Petit cercle, triangle, ou sprite Au debut, un petit cercle suffit.

Ordre de dessin

Arcade dessine dans l'ordre des appels. Ce qui est dessine en dernier apparait au-dessus. Pour Fly-in, l'ordre naturel est:

  1. Effacer l'ecran avec self.clear().
  2. Dessiner les connexions.
  3. Dessiner les zones.
  4. Dessiner les drones.
  5. Dessiner les labels et l'interface.
def on_draw(self) -> None:
    self.clear()
    self.draw_connections()
    self.draw_zones()
    self.draw_drones()
    self.draw_hud()

Couleurs des maps

Le sujet dit que les couleurs sont des strings libres comme red, blue ou gray. Arcade attend une couleur sous forme de tuple RGB/RGBA ou une constante comme arcade.color.RED. Il faut donc une petite table de conversion. 

COLOR_BY_NAME: dict[str, tuple[int, int, int]] = {
    "red": (220, 70, 70),
    "green": (70, 180, 90),
    "blue": (80, 130, 230),
    "yellow": (230, 210, 70),
    "gray": (120, 130, 145),
}


def color_from_metadata(color_name: str | None) -> tuple[int, int, int]:
    if color_name is None:
        return (90, 120, 180)
    return COLOR_BY_NAME.get(color_name.lower(), (160, 160, 180))

8. Separateur important: etat, simulation, rendu

Le plus gros risque avec Arcade est de melanger les responsabilites: faire du pathfinding dans on_draw, modifier la simulation en dessinant, ou faire dependre l'algorithme du nombre de FPS. Il faut separer les couches.

Donnees statiques

Map, Zone, Connection. Viennent du parser. Ne changent pas pendant le rendu.

Etat de simulation

Tour actuel, position logique de chaque drone, mouvements prevus, drones livres.

Etat visuel

Positions interpolees en pixels, animation en cours, zone selectionnee, pause, vitesse.

Regle simple

on_draw doit etre presque pur: il regarde l'etat courant et dessine. on_update peut modifier l'etat visuel. Ton moteur de simulation doit pouvoir etre teste sans ouvrir une fenetre Arcade.

Pourquoi c'est important pour 42?

En evaluation, on peut te demander d'expliquer ou modifier une partie. Si tout est melange dans les callbacks graphiques, tu ne sauras plus si un bug vient de l'algo, du parser ou du dessin. Une separation claire rend ton projet plus defendable.

9. Animation et simulation tour par tour

Fly-in est discret: tour 1, tour 2, tour 3. Arcade est continu: il dessine par frames, par exemple environ 60 fois par seconde. Tu dois relier les deux sans casser les regles du sujet.

Simulation

Un drone passe de roof1 a roof2 au tour suivant.

Visualisation

Entre deux tours, Arcade peut animer le cercle du drone de la position A vers B.

delta_time

delta_time est le temps ecoule depuis le dernier update, en secondes. Si ton animation doit durer 0.35 seconde, tu accumules le temps et tu calcules une progression entre 0.0 et 1.0. 

def lerp(start: float, end: float, progress: float) -> float:
    return start + (end - start) * progress


elapsed += delta_time
progress = min(1.0, elapsed / animation_duration)

current_x = lerp(start_x, end_x, progress)
current_y = lerp(start_y, end_y, progress)

Zones restricted

Dans le sujet, entrer dans une zone restricted coute 2 tours. Visuellement, tu peux representer le drone sur la connexion pendant le premier tour, puis dans la zone a l'arrivee. Mais la regle importante reste logique: le drone ne choisit pas d'attendre sur la connexion. Arcade ne doit qu'afficher cet etat.

Ne confonds pas duree graphique et cout de simulation. Une animation de 0.35 seconde ne signifie pas que le mouvement coute 0.35 tour. Les tours appartiennent a ton moteur de simulation, les secondes appartiennent a Arcade.

10. Entrees clavier et souris

Les entrees te permettent d'explorer la simulation, ce qui est tres utile pour apprendre et pour debugger.

Entree Callback Arcade Usage utile dans Fly-in
Space on_key_press Avancer d'un tour manuellement.
P on_key_press Pause ou reprise de la lecture automatique.
R on_key_press Reset visuel ou simulation.
Clic gauche on_mouse_press Selectionner une zone pour afficher type, capacite, drones presents.
Molette on_mouse_scroll Optionnel: zoomer si la carte est grande. 
def on_key_press(self, symbol: int, modifiers: int) -> None:
    if symbol == arcade.key.SPACE:
        self.advance_one_turn()
    elif symbol == arcade.key.P:
        self.paused = not self.paused
    elif symbol == arcade.key.R:
        self.setup()

Le point important est que advance_one_turn devrait appeler ton moteur de simulation ou lire un historique deja calcule. Ce n'est pas Arcade qui doit inventer le mouvement valide.

11. Comment l'integrer progressivement au projet

Ne branche pas tout d'un coup. Ajoute Arcade par petites etapes validables.

  1. Faire une fenetre vide avec un titre Fly-in viewer.
  2. Passer une Map parse a une SimulationView.
  3. Calculer les positions ecran de toutes les zones.
  4. Dessiner les connexions et les zones sans drones.
  5. Afficher les labels, couleurs et types de zones.
  6. Ajouter un drone fictif qui avance sur un chemin fixe pour apprendre l'animation.
  7. Brancher ensuite ton vrai historique de simulation.

12. Pieges classiques avec Arcade

Oublier arcade.run()

La fenetre se cree puis rien ne se passe, car la boucle d'evenements ne demarre pas.

Oublier self.clear()

L'image precedente reste et l'affichage devient sale.

Modifier la simulation dans on_draw

Le resultat depend du FPS. C'est dangereux pour un projet tour par tour.

Confondre pixels et coordonnees de map

Les positions du fichier ne sont pas directement adaptees a la fenetre.

Multiplier les fenetres

Arcade est pense pour une seule fenetre. Utilise des View pour plusieurs ecrans.

Tout faire avec des sprites trop tot

Pour un graphe, les primitives de dessin sont plus simples pour commencer.

13. Exercices pour apprendre sans copier une solution

Fais ces exercices dans l'ordre. Chacun valide un concept Arcade precis. Si un exercice bloque, c'est le signe que ce concept doit etre retravaille avant de coder la visualisation complete.

Exercice 1: fenetre minimale

Cree une fenetre 900x600 avec un fond noir et le texte Fly-in au centre. Objectif: comprendre Window, on_draw, self.clear(), arcade.run().

Exercice 2: une View propre

Reecris l'exercice 1 avec arcade.View et window.show_view(view). Objectif: comprendre la difference entre fenetre et ecran logique.

Exercice 3: dessiner une map statique

Parse maps/easy/01_linear_path.txt, transforme les coordonnees en pixels, dessine les zones et connexions. Objectif: relier parser.py a Arcade sans simulation.

Exercice 4: selection de zone

Au clic, detecte la zone la plus proche et affiche son nom, son type, sa couleur et sa capacite. Objectif: apprendre l'input souris et le debug visuel.

Exercice 5: animation fictive

Sans pathfinding, anime un point de start vers waypoint1, puis vers waypoint2. Objectif: comprendre delta_time et l'interpolation.

Exercice 6: lecture tour par tour

Cree une liste fictive de mouvements par tour et avance avec Space. Objectif: separer simulation discrete et rendu continu.
